## State and side effects

The separate SQLite `publishing-v1/publishing.sqlite` stores owned account mappings, one-use connection states, post revisions, per-destination execution, provider operation reservations, expiring hashed delivery grants and worker heartbeats. It does not change media-job kinds or retry contracts. SQLite WAL/FULL synchronous transactions reserve each dispatch and fenced operation. At most two destination claims run per host.

Persist the operation reservation before invoking an external mutation. Persist container/media/post IDs before advancing. A timeout, HTTP5xx or incomplete mutation receipt can mean acceptance; move to reconciliation/unknown, never retry the mutation automatically. A successful destination is never selected by retry. Explicitly rejected requests may be retried only through the failed destination action. Read-only receipt checks can resume after restart. A worker dying after upload registration can leave an orphan upload; this is not claimed as a published Pin.

The app stores the chosen wall time, IANA zone, resolved UTC instant and offset. Gaps are rejected. Repeated DST times require an explicit earlier/later choice. Schedule creation must persist before showing confirmation. Editing requires the latest post revision and all destinations to remain undispatched.

## Export and private delivery contract

`CompletedExportRef={projectId,fileKey}` contains only a flat registered MP4 key. Resolution verifies the owner, current project, registry membership, regular nonempty file, bounded ffprobe metadata and a streamed SHA256 under a private storage lease. No arbitrary client URL, path, identity or plan metadata is accepted. Both existing SSE and durable-job exports work through the same registered-file contract. Original plan settings/fingerprint are optional and must come from a matching authoritative receipt, never inferred from a saved plan.

The dispatch revalidates the content hash. Public delivery uses a new random capability, stored only as SHA256 and scoped to one owner/project/export/destination. Every request revalidates ownership, registration, grant and connection. GET/HEAD and one byte range only; no listing. An active stream holds a storage lease and stops on abort, expiry, disconnect or grant revocation. The private media tree remains private. Default grant lifetime should be short, with at most six hours only for documented asynchronous fetching. Never reuse renderer capabilities or auth cookies in provider requests.

Deletion integration must call the publishing admission fence **unconditionally before** `storage.deleteProject`, including when a project has no media jobs. `beginProjectDeletion(owner,pid)` verifies current ownership first, commits an admission tombstone, cancels undispatched work, revokes grants/stops streams, and returns readiness plus unresolved destination IDs. New enqueue and mutation reservations must reject closed admission. If a side effect is unresolved, keep files and return409. Main owns wiring this into existing delete routes. Account removal uses the owner fence; no new public account-delete endpoint is implied.

## Preferred upload routes without app public hosting

The current [Instagram integration guide](https://docs.composio.dev/kb/guide/toolkits-instagram) explicitly supports staged local video via `INSTAGRAM_POST_IG_USER_MEDIA.video_file`. The [Files presign endpoint](https://docs.composio.dev/reference/api-reference/files/postFilesUploadRequest) takes the exact toolkit/tool, server-generated filename, MIME type and MD5, returning a new file ID, storage key and signed PUT URL. The implementation matches the official [file upload utility](https://github.com/ComposioHQ/composio/blob/next/ts/packages/core/src/utils/fileUtils.node.ts): PUT the selected bytes with Content-Type, then pass `{name,mimetype,s3key}` to the tool. It uses a filesystem-backed Blob so upload bytes stream without buffering an entire export. Only a trusted AWS S3 destination is allowed; social/API credentials are never forwarded to it.

The operation is reserved before file staging. Its file ID/timestamp is journaled before bytes are sent; signed URLs and storage keys remain only in memory and never enter SQLite, frontend DTOs or logs. Container and final post receipts keep the existing ambiguity/fencing rules. The user-approved test must cover the selected upload and public post; no real file has been staged yet.

Pinterest's current official [OpenAPI 5.32.0 video source schema](https://github.com/pinterest/api-description/blob/main/v5/openapi.yaml) supports `cover_image_key_frame_time` in integer seconds; the preferred adapter uses that after the registered S3 video upload. An app-hosted cover URL is unnecessary. The actual keyed integration schema and an approved live Pin still need verification.

Preferred operator defaults are `UNFOLD_PUBLISHING_INSTAGRAM_DELIVERY=staged_file` and `UNFOLD_PUBLISHING_PINTEREST_COVER=key_frame`. These do not require a public app origin or public delivery flag. Explicit `public_url` fallback uses the existing owner-bound expiring delivery grants and still requires trusted HTTPS delivery configuration. No tunnel has been created.

Staged-file retention, verified2026-11-22: the current [data-retention policy](https://docs.composio.dev/docs/security/data-retention#how-long-files-are-available) explicitly covers files a tool uses or returns. It states that staged objects are automatically deleted after24hours. Presigned URLs default to one hour and can be configured up to24hours; URL expiry does not delete the underlying object. The [token-custody documentation](https://docs.composio.dev/docs/security/token-custody#where-payloads-go-and-how-long-they-stay) corroborates this distinction. The public Files API has no documented per-object deletion endpoint, so local project deletion cannot promise immediate external erasure. Keep the approved upload's retention disclosure accurate and do not change project-wide settings silently. Tool-call arguments/results have a separate default log-retention policy of up to one year; project ZDR has feature and managed-app exclusions. No stronger deletion or ZDR guarantee has been configured or tested here. Current direct Meta resumable examples require Facebook Login for Business; the app does not assume the Instagram Business Login connection has those credentials. The documented proxy base64 limit is4MB, so it is not the large-video path.
